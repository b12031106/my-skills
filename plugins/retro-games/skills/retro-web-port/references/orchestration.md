# 子代理分工與模型規則

## 選擇與授權

本 skill 明確授權主控在專案任務範圍內自主使用子代理工具：建立／喚起、分派、接續、協調、停止自己的子代理，以及按下表選擇或調整可用模型與思考等級。不需每次向使用者詢問是否可以派遣。主控對有獨立交付價值的任務應採取實際委派行動，再確認產物及驗收結果；不得只提出分工計畫就停止。權限與預算仍依使用者及宿主限制。

以下為 Codex 與 Claude Code 的預設分工政策，允許在實際開發委派時依任務套用相應欄位的模型／思考等級。這是按任務角色的建議，不代表兩家模型能力或成本完全等價。其他 coding agent 按 [跨 agent 適配](agent-compatibility.md) 選本地模型。使用者明確指定模型、成本上限或不准委派時，以其指示為準。先檢查環境實際提供的模型、思考等級及並行限制；名稱不是永久能力或價格保證，不虛構不存在的選項。

**可驗證的低／中風險子任務先試較省成本的模型，不把輕量模型限定為只能整理資料。** Claude 預設先試實際可用的 Haiku，再依交付品質升 Sonnet、Opus；Codex 先試 Luna，再升 Sol，關鍵疑難才用 Astra。這是各自環境的分工梯度，不是跨廠商能力等價。主控及未知逆向／高影響共用狀態可直接使用較強模型，寫明跳級理由，不必機械式逐級試錯。

| 工作 | Codex 模型／思考等級 | Claude Code 模型／effort | 判斷條件 |
|---|---|---|---|
| 主控、拆解、整合與一般覆核 | GPT-6.1 Sol／medium | Sonnet (`sonnet`)／medium | 重要逆向與跨系統簽核可交由 Sol／high 或 Opus／high |
| 局部實作、介面、測試、人工存檔製作 | GPT-6 Luna／high 起步，需升級時 Sol／medium 或 high | Haiku (`haiku`)／預設起步，需升級時 Sonnet／medium 或 high，再到 Opus／high | 規則已有證據、介面明確、範圍受控且結果可獨立核對；主控確認後才接受 |
| 未知原版規則、組合語言、AI、亂數、存檔與共用狀態 | GPT-6.1 Sol／high | Opus (`opus`)／high | 需要建立證據或跨模組推理 |
| 換方法仍卡住的關鍵難題 | GPT-6 Astra／high | Opus (`opus`)／xhigh（若支援，否則 high） | 限定一個高影響問題，不設為日常預設；先換證據或縮小案例，再提高 effort |
| 簡單資料整理、檔案清單與固定步驟結果核對 | GPT-6 Luna／medium | Haiku (`haiku`)／模型預設 | 無未知規則、結果可直接核對；不承擔原版逆向或關鍵簽核 |
| 工程流程操作與問題記錄；最後依需求正常遊玩 | GPT-6 Luna／high 起步 | 明確檢查點與步驟可先試 Haiku，需升級時 Sonnet／medium | 先用 debug／god mode 排除難度障礙，實際觸發流程；長流程拆成可恢復批次，不讓模型反覆正常打法敗北 |

Claude Code 使用實際可用的模型別名，不把版本號寫死。表中 effort 是建議值，只有該版本／模型支援時才設定；Haiku 不預設支援可調 effort。無法單獨設定時沿用宿主設定並說明實際值，不宣稱已套用。Claude 子代理的 `effort` 與 extended thinking 開關是不同設定，不能以其中一項冒充另一項；環境或政策也可能覆蓋要求的設定。參考 [Claude Code 子代理模型與 effort](https://code.claude.com/docs/en/sub-agents)。

主 session 的模型若不能由工具切換，不宣稱已切換；在現有模型下總控，必要時委派可用的調查者。指定子代理模型須使用工具支援的上下文模式；若完整歷史繼承不支援覆寫，改用局部歷史或明確任務資料。沒有指定模型能力時沿用可用模型，不自行創建新 session 當替代。

以未知程度、影響範圍與失敗代價決定模型，而非程式碼行數。較輕量或一般模型連續失敗時先分析／縮小問題，再交由較強模型；不能讓便宜代理無限重試。Claude 可由 Haiku 升至 Sonnet，涉及未知逆向則交由 Opus；不是所有任務都要逐級嘗試。高思考、重複傳背景、多人重跑和返工都會提高總用量，不能保證低階模型必然省錢。只在要討論當前價格或產品限制時查官方資訊。

## 依交付結果校正分派

委派前讀專案既有模型觀察紀錄；沒有時建立 `docs/MODEL-ROUTING.md`（或沿用專案已有同用途文件），並從 TODO 連結。這是跨 session 可讀取的路由紀錄，不只留在聊天或某工具私有記憶。每批由主控更新，不讓多個子代理同時寫同一份紀錄。

首次使用某模型／版本時，挑一個真實、低風險且可直接核對的待辦試用，例如存檔副本 hash 清單、TODO 文件連結稽核，也可以直接選規格完整、影響受控的小型 UI 修正／工具製作；不強制先做文件稽核才能寫程式。依交付可靠度逐步擴大適用任務。不要為測模型而製造無關任務或讓多個模型反覆做同一件已完成的事。

每筆至少記錄：日期、專案／任務與產物、請求及實際模型／版本／effort（無法得知就寫未知）、任務類型及風險、背景／工具／debug 條件、主控確認的結果、失敗類型與原因、重試／返工、可取得的耗時／用量、後續分派建議與可信度。沒取得計量時不推算虛構費用；單次成功或失敗只能形成有限觀察。

升級依序判斷：

1. 區分模型交付缺陷、任務契約不清、環境／權限／缺證據，以及測試方法不當；失敗先記原因。純環境／服務失敗另記，不算模型能力失敗次數；環境恢復後可同級重跑，但仍受工作量／檢查點限制，不能無限嘗試啟動服務。打不贏或資金不足優先改 debug 狀態，不能因換強模型較會打就認定弱模型不適合驗收。
2. 輕量模型交付不合格時，帶著原產物、具體差異及最小重現改派下一級，不從零重做。只有明確可修正的上下文／工具問題才留在同級修正一次；同一問題最多兩次無進展就改方法或升級，主控可因影響大而立即升級。
3. 中階仍不合格才交較強模型；遇未知原版逆向、存檔破壞風險或跨模組共用狀態，可直接跳級。升級後仍遵守相同的檔案、證據及測試範圍限制。
4. 可靠交付後調整下一次「相似任务」路由；不因一次工具製作成功就認定該模型能處理全部逆向，也不因正常玩法失敗就否定它的分類／診斷能力。能力足夠時維持或降低成本，避免只會升級不會重新試較省成本選項。

使用者提供的其他 session 經驗可記為「使用者轉述、待本專案驗證」的起始線索，不得偽造本地觀察。只讀 hash／連結稽核成功、某模型打法被動、較強模型無範圍限制時測試過久，分別反映不同的能力／方法／契約問題；不把它們合併成單一模型排名。跨專案重用可搬運不含原始遊戲／私人資料的任務類型結論，仍注明來源與適用條件，不自動向外部服務共享記憶。

紀錄可用這個表格，資料不足可保留未知，不需硬湊評分：

| 日期／任務 | 實際模型／effort | 類型／風險／條件 | 主控驗收與證據 | 原因／返工／已知用量 | 下次路由／可信度 |
|---|---|---|---|---|---|

## 測試範圍與工作量契約

所有模型都受相同限制，尤其不能因使用較強模型就默許數小時無邊界驗收。每次任務列明要測的入口／狀態、相關測試檔或既有檢查、必要 UI 操作、何時交付及何種發現需回報主控。高成本項給合理的時間／回合檢查點與部分交付條件；這是子任務管理，不擅自修改整體 Goal 的預算或完成範圍。

子代理不自行擴增為整套回歸、全章節重播、多 seed 長跑或正常難度全程遊玩。只有主控在本次任務契約明確指派時才能執行這些檢查；超出預期耗時就提交已完成結果、失敗／缺口與下一步，不用反覆測試填滿時間。主控指定一個整合驗收負責者集中執行必要的整體回歸，其他代理只做分配的相關檢查。

期限／回合上限到了是部分交付，不是功能完成。新的具體失敗需要補測時，先列最小新增案例與理由，由主控重新分派或自行執行；已有規則允許自主調度，無需把每次調整交回使用者。

## 任務契約

每個任務交付這些資訊，篇幅隨任務調整：

- TODO 編號、具體缺口、玩家影響與完成範圍。
- 原版證據位置、可信度、需要查證的未知；不能以猜測補齊的欄位。
- 接口與前後狀態、允許修改檔案、不得修改的共用區域。
- 最小驗收案例、固定亂數／存檔來源、需要的 UI 操作及預期結果。
- 本次指定的檢查範圍、工作量／進度檢查點、部分交付條件與禁止自行啟動的長測試；模型選擇理由及參考的觀察紀錄。
- 通關任務明示可使用的 debug／god mode 與數值輔助；若沒有工具，允許在所分配範圍建立最小測試入口。驗收模式是工程流程或正常數值、哪些觸發不得跳過、哪些規則需另做未輔助案例，都要說清楚。
- 回報需包含改動、證據、實際執行的檢查、限制與產物位置。

可以交付研究任務，但需有可用於後續實作的具體結論或不可判定邊界；避免產出沒有接入用途的大型報告。實作完成不包括自行 push、部署或替主控核准整體功能。

## 並行與所有權

依實際並行額度保留主控及必要覆核空間；額度四人時可先採主控＋兩名開發＋一個彈性調查／覆核席。沒有獨立任務就不用填滿名額。

多人不得同時寫相同檔案；最初由主控分配所有權。核心入口、共用狀態、TODO 與最後整合通常由主控持有。拆不開的改動序列化；或按專案既有慣例用隔離工作樹並由主控整合，不為並行而丟失尚未提交的修改。

瀏覽器、原版遊戲視窗與共用測試服務屬可變資源：輪流操作或使用獨立 origin／profile／連接埠，不可互相覆寫畫面與儲存。測試服務記錄所有者及識別，只停止自己啟動的服務。

相關任務可沿用已理解該系統的代理；領域切換或上下文污染時才換新代理。不要每個小步都重建全部背景。子代理不能無限制再委派；主控掌握全隊額度與檔案所有權。

## 簽核與接續

子代理自測 → 主控讀實際差異與原版證據 → 整合 → 針對受影響路徑重現關鍵操作 → 必要回歸 → 主控更新 TODO → 派下一批。

主控不必重跑子代理每一項低風險檢查；依改動檢查可信證據。跨狀態、共用亂數、存檔和關鍵流程必須在整合版本確認。測試預期如果直接來自新實作本身，不能當作獨立原版 oracle。

未能簽核就保留未完成／部分完成及原因，不以代理回報數量衡量進度。對失敗回覆具體差異與新的查證方向；完成一項不需向使用者詢問是否繼續。
