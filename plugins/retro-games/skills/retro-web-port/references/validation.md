# 驗收、測試存檔與完成門檻

## 用最短流程驗足夠範圍

選能直接區分正確與錯誤的案例。避免每次從第一關開始，也避免把「最小驗收」解讀成只有一個 happy path。

優先順序：既有合法檢查點副本 → 已知格式的原存檔副本 → 有來源的固定初始狀態 → 明示人工狀態。依本次問題選最低成本的有效方式；不強迫每項都操作原版。

人工狀態可修改進度、位置、HP、EXP、物品、事件旗標與亂數，但須符合已知結構、不變量與進入條件。記錄原始模板及改動欄位；相關狀態有不明耦合時先查證，不能隨意補零。不要用直接呼叫內部函式替代需要檢查的真正入口。

原版和 Web 能使用同狀態／操作／亂數時逐步比對；亂數無法固定時比較已證實的不變量、合法結果與消耗路徑，不能宣稱精確對拍。

## 工程通關與 debug／god mode

流程驗收的問題是「實際觸發能否順利抵達下一場景／結局」，不是「代理是否能靠正常難度打贏」。先消除與本次驗收無關的戰力、資源與時間障礙。主控與子代理已獲授權自行使用下列隔離測試方法：

- 增強主角／隊友攻防、移動或 HP，測試限定鎖血／無敵，降低敵方能力或 HP；使用符合欄位範圍的值，避免數值溢位造成假問題。
- 增加金錢、補滿物品，調整商店／店員的相關交易資料、庫存或價格，快速进入買賣、裝備、整備與下一場景；不把無關人物欄位亂改成未知值。
- 使用章節／任務檢查點定位，或加入最小 debug 入口／測試 overlay／狀態注入工具。工具應預設關閉、可撤銷，與玩家存檔及正式規則隔離；記錄原值、改動和撤銷方式，不修改原始遊戲資料。

進入場景後仍從真正玩家／AI 入口走過命令、勝敗判定、戰後事件、獎勵、隊伍承接、下一章和結局。必須保留被驗證的觸發條件，不能直接寫入「勝利／已完成／結局」或直接呼叫結局來冒充流程驗收。直接跳章節適用於局部定位，被跳過的連線另行驗證。

修改狀態需針對驗收目標選擇：鎖血會遮蔽死亡／敗北，高攻擊可能遮蔽反擊／敵軍回合，高等級可能遮蔽 EXP／轉職，低價或高資金會遮蔽不足金額判定。這些分支用解除輔助或專門人工門檻案例驗證，不以要求全程正常遊玩代替。測正常傷害／價格／成長等規則時，保留該項原版數值，其他不相關條件可以加強。

卡在打不贏、資金不足、練等或反覆操作時立即改用上述方法；同一障礙最多兩次無進展就換測試條件或補 debug 工具。區分遊戲 bug 與測試策略成本；不得把正常難度造成的進度停滯當成只能交回使用者的阻礙。

報告標示「debug 輔助流程通關」，列出輔助項及真正走過的觸發／場景／結局；不要寫成「正常難度自然破關」。驗證完確認 debug 關閉後原本預設與保存行為可恢復。

## 驗證層次與證據

| 層次 | 需要確認 | 不能推論 |
|---|---|---|
| 原始資料／程式規則 | 格式、欄位、分支、呼叫與讀寫來源 | Web 已接入或原機實際行為全覆蓋 |
| 純資料／底層測試 | 獨立來源向量、邊界、錯誤／取消及狀態不變量 | 玩家流程已完成 |
| 呼叫端整合 | 真入口、對象身份、共享狀態、失敗／重試、結果承接 | UI 操作與畫面已正確 |
| 局部實際遊玩 | 畫面、輸入、前後狀態、返回可繼續操作 | 從頭到尾可破關 |
| 工程完整流程（優先） | 可用 debug 輔助，實際觸發事件／跨關／保存恢復並抵達結局 | 正常難度、平衡或被輔助遮蔽的規則已驗證 |
| 正常數值自然流程（最後、依需求） | 不使用數值輔助的合法起點連續推進、保存恢復、必要分支與結局 | 未覆蓋的原硬體或歷史狀態完全等價 |

完成條件對應任務範圍。資料解碼可以在資料核對後完成；玩家功能則需要接入及實際操作。尚未原機對照時寫明哪部分只經 Web 驗證。

## 常見驗收設計

- **戰鬥／能力／AI**：固定人物、地形、裝備、HP 與亂數；從玩家命令或真正 AI 入口觸發，比較傷害、命中、反擊、EXP、物品及亂數前後。覆蓋本次改動涉及的死亡、零收益、上限與特殊對象。
- **事件／跨關**：用檢查點到觸發前一步，再經實際操作觸發；核對旗標、隊伍、獎勵及下一場景。僅跳到事件後驗畫面不能驗觸發與承接。
- **商店／背包**：觸發對話、選購／取消、金錢和物品變化、適用角色／比較、返回操作；按改動覆蓋不足金額或空間等邊界。
- **存讀檔**：保存前快照 → UI 保存 → 改變狀態 → UI 讀取 → 比較持久欄位及可繼續操作。核對隊伍、裝備、物品、場景、事件、回合與亂數等該格式表示的狀態；明示不表示的前史。Web 往返與原版讀回是不同任務。
- **畫面／輸入／加強操作**：至少實際查看改動畫面並操作；驗證縮放／平移／對話或動畫前後、快速輸入、取消等受影響行為。不能只測繪圖 helper 或按鈕存在。

用專案既有瀏覽器／測試工具；工具不足時先完成可驗證部分並保留 UI 未驗證項，不冒充已實際操作。不得覆寫玩家存檔；獨立 origin 也應使用不同測試識別，避免其他代理相撞。

## 回歸、工程通關與最後正常遊玩

每批改動跑相關檢查；只有新修改、失敗或新疑點才重複同一批驗證。主控在整合里程碑及最終候選版跑整體測試，記錄版本與範圍，不把新增加的測試算入舊的整體通過數。

先做局部驗收及 debug 輔助的連續流程通關，排除所有已知的基礎流程障礙。正常數值／難度驗收只在這些工作之後，依使用者目標安排；如果 Goal 明確要求自然破關，保留該項未完成，不因 debug 通關把它勾選，也不讓它阻止前面的工程工作。

兩種模式都沿途保存可恢復檢查點，遇錯誤從受影響的最早檢查點重驗；只有根本狀態／全域規則改變使舊檢查點失效時才重建起點，不盲目每次整個重來。

完整流程須能串接關卡／章節、劇情、成長、戰鬥、整備、存讀與結局，依作品納入重要分支。必要的人工分支案例可補覆蓋，但不能標成自然破關。驗收後仍有改動則重驗受影響流程，完整流程紀錄明列適用版本。

## 每批交付的證據

記錄 TODO 編號、改動／來源位置、模板或人工狀態及 seed、操作序列、預期值來源、實際結果、驗證版本、未覆蓋範圍。截圖或日誌按專案既有保留政策存放；沒有執行的測試不能列為通過。
